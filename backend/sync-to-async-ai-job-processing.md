# AI 모델 호출을 동기 API에서 비동기 Job으로 분리하는 기준

## 처음에는 동기 호출이 가장 단순하다

AI 모델 호출 기능을 처음 구현할 때 가장 단순한 방식은 동기 API 호출이다.

사용자가 요청을 보내면 API 서버가 외부 AI Provider를 호출하고, 응답을 받아 다시 사용자에게 내려준다.

```text
Client → API Server → AI Provider → API Server → Client
```

이 구조는 이해하기 쉽다. 별도의 Job Store나 Worker가 필요하지 않고, 사용자는 요청에 대한 결과를 바로 받는다. 실패 처리도 단순해 보인다. Provider 호출이 실패하면 API 응답을 실패로 내려주면 된다.

작업 시간이 짧고 결과가 바로 필요한 기능이라면 이 방식이 충분할 수 있다. 모든 AI 호출을 처음부터 비동기 Job으로 만들 필요는 없다. 구조가 단순할수록 개발과 디버깅도 쉽다.

하지만 이미지 생성, 영상 생성, 외부 모델 추론처럼 작업 시간이 길어질 수 있는 기능에서는 동기 호출의 한계가 빠르게 드러난다.

## 동기 호출의 한계

동기 호출의 가장 눈에 띄는 문제는 사용자 대기 시간이다. Provider 응답이 몇 초 안에 안정적으로 끝나면 큰 문제가 없지만, 응답 시간이 길어지거나 편차가 커지면 사용자는 요청이 멈춘 것처럼 느낄 수 있다.

서버 입장에서도 부담이 생긴다. API 서버는 Provider 응답을 기다리는 동안 요청 context를 유지해야 한다. 동시 요청이 늘어나면 대기 중인 요청이 많아지고, connection이나 worker 자원을 오래 점유하게 된다.

또 다른 문제는 실패 경계가 모호해진다는 점이다.

예를 들어 API 서버에서 timeout이 발생했다고 해서 Provider 쪽 작업이 실제로 취소되었다고 단정할 수 없다. 서버는 응답을 받지 못했지만, Provider는 요청을 이미 수락해 작업을 진행 중일 수 있다. 이 상태에서 사용자가 다시 요청하거나 서버가 retry를 수행하면 같은 작업이 중복 실행될 수 있다.

따라서 동기 호출의 문제는 단순히 “느리다”가 아니다. 긴 외부 작업을 사용자 요청 생명주기와 강하게 묶어버리는 것이 핵심 문제다.

## 비동기 Job으로 분리한다는 것

비동기 Job으로 분리한다는 것은 사용자 요청과 실제 Provider 호출을 분리한다는 뜻이다.

흐름은 보통 다음처럼 바뀐다.

```text
1. Client가 생성 요청을 보낸다.
2. API Server는 Job을 생성하고 jobId를 반환한다.
3. Worker가 Job을 가져와 Provider를 호출한다.
4. Worker가 결과를 저장하고 Job 상태를 갱신한다.
5. Client는 jobId로 상태나 결과를 조회한다.
```

구조로 보면 다음에 가깝다.

```text
Client
  ↓
API Server
  ↓
Job Store / Queue
  ↓
Worker
  ↓
AI Provider
  ↓
Object Storage / Job Status
```

이 구조에서는 API 서버가 Provider 응답이 끝날 때까지 기다리지 않아도 된다. API 서버는 작업 접수와 상태 조회에 집중하고, 실제 긴 작업은 Worker가 담당한다.

사용자 입장에서는 즉시 결과를 받는 대신 `queued`, `processing`, `succeeded`, `failed` 같은 상태를 보게 된다. 프론트엔드는 polling으로 상태를 조회하거나, 별도의 이벤트 흐름을 통해 완료를 알릴 수 있다.

## 언제 비동기 분리를 고려할까

비동기 구조가 항상 더 좋은 것은 아니다. Job Store, Queue, Worker, 상태 조회 API, 중복 실행 방지 같은 추가 책임이 생긴다. 사용자 경험도 달라진다. 요청을 보내자마자 결과를 받는 대신, 작업 상태를 기다리는 흐름을 설계해야 한다.

그래서 기준 없이 “AI 호출은 비동기로 처리해야 한다”고 일반화하는 것은 좋지 않다.

비동기 분리를 검토할 만한 상황은 다음과 같다.

```text
- Provider 응답 시간이 길거나 편차가 크다.
- API timeout 안에 안정적으로 끝난다고 보기 어렵다.
- 결과 파일을 별도 저장소에 보관해야 한다.
- 실패 후 재시도나 복구가 필요하다.
- 같은 요청이 중복 실행되면 비용 문제가 생긴다.
- 사용자에게 작업 진행 상태를 보여줘야 한다.
- 운영자가 backlog, retry, 실패율을 관찰해야 한다.
```

이 조건이 많아질수록 동기 호출보다 비동기 Job 구조가 더 현실적인 선택지가 된다.

반대로 작업이 짧고, 실패 비용이 낮고, 결과를 즉시 내려주는 것이 중요한 기능이라면 동기 호출이 더 단순하고 적절할 수 있다.

## 비동기 구조가 만드는 새로운 책임

비동기 구조는 API timeout 문제를 줄여주지만, 새로운 책임을 만든다.

먼저 Job 상태를 저장해야 한다. 사용자가 요청한 작업이 대기 중인지, 처리 중인지, 성공했는지, 실패했는지 알 수 있어야 한다.

또 Worker를 운영해야 한다. Worker는 Job을 가져와 Provider를 호출하고, 결과를 저장하고, 상태를 갱신한다. Worker가 죽거나 Provider 호출 중 장애가 발생했을 때 어떻게 복구할지도 생각해야 한다.

중복 실행도 고려해야 한다. 같은 Job이 두 번 처리되면 Provider 비용이 중복 발생할 수 있고, 결과가 여러 개 생길 수 있다. 따라서 Job을 가져가는 방식, 처리 중 상태 전환, retry 기준, idempotency 같은 요소가 필요해진다.

즉 비동기 구조는 느린 작업을 단순히 뒤로 미루는 장치가 아니다. 긴 외부 작업을 서비스가 상태로 관리하기 위한 구조다.

## 동기와 비동기를 함께 사용할 수도 있다

실무에서는 모든 요청을 하나의 방식으로만 처리하지 않을 수 있다.

예를 들어 빠르게 미리보기 결과를 만들 수 있는 작업은 동기 호출로 처리하고, 고해상도 결과 생성이나 후처리가 필요한 작업은 비동기 Job으로 분리할 수 있다. 또는 초기에는 동기 호출로 시작하고, 작업 시간이 길어지거나 운영 문제가 드러나는 시점에 비동기 구조로 옮길 수도 있다.

중요한 것은 동기와 비동기를 기술 취향으로 고르는 것이 아니라, 작업의 성격과 실패 비용을 기준으로 선택하는 것이다.

## 정리

AI 모델 호출을 동기 API에서 비동기 Job으로 분리하는 기준은 단순히 “느리니까 비동기”가 아니다.

핵심은 긴 외부 작업을 사용자 요청 생명주기와 분리할 필요가 있는지다. 작업이 짧고 실패 비용이 낮다면 동기 호출이 충분히 좋은 선택일 수 있다. 하지만 작업 시간이 길고, 결과 저장이 필요하며, 실패 후 재시도와 상태 관리가 중요해지는 순간 동기 호출은 부담이 된다.

비동기 Job 구조는 API 서버와 Worker의 책임을 나누고, 작업을 상태로 관리할 수 있게 해준다. 대신 Job Store, Worker 운영, 상태 조회, retry, 중복 실행 방지라는 새로운 책임을 함께 가져온다.

따라서 판단 기준은 다음처럼 정리할 수 있다.

> AI 호출이 사용자 요청 안에서 안정적으로 끝나지 않거나, 실패 이후의 상태를 서비스가 관리해야 한다면 비동기 Job으로 분리하는 편이 현실적이다.
