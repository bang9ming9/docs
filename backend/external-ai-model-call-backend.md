# 외부 AI 모델 호출을 백엔드에서 다룰 때의 기본 책임

## 왜 단순 API 호출처럼 보기 어려운가

백엔드에서 외부 API를 호출하는 일은 흔하다. 결제 API, 알림 API, 지도 API, 파일 저장소 API처럼 서비스 바깥의 시스템을 호출하고 결과를 받아오는 구조는 익숙하다. 그래서 처음에는 외부 AI 모델 호출도 비슷하게 생각하기 쉽다.

사용자 요청을 받고, 서버에서 AI Provider API를 호출하고, 응답을 받아 다시 사용자에게 내려주면 된다. 코드만 보면 HTTP client를 하나 만들고 request/response 구조체를 정의하는 정도로 시작할 수 있다.

하지만 실제 서비스 흐름 안에 AI 모델 호출을 넣어 보면 일반적인 API 연동보다 더 신경 써야 할 부분이 많다. 호출 시간이 길 수 있고, 실패 원인이 다양하며, 같은 요청을 다시 보내는 것이 추가 비용이나 중복 결과 생성으로 이어질 수 있다. 결과가 텍스트처럼 바로 응답되는 경우도 있지만, 이미지나 영상처럼 파일 형태로 만들어져 별도 저장소에 보관해야 하는 경우도 있다.

이 글에서는 외부 AI 모델을 호출하는 백엔드 서버가 단순히 Provider API를 감싸는 wrapper가 아니라, 서비스 요청과 외부 AI 작업 사이의 책임 경계라는 관점에서 정리한다.

## 클라이언트가 직접 Provider를 호출하지 않는 이유

가장 먼저 떠올릴 수 있는 이유는 API key 보호다. 외부 AI Provider를 호출하려면 보통 인증키가 필요하고, 이 키가 클라이언트에 노출되면 의도하지 않은 호출이나 비용 문제가 생길 수 있다. 브라우저나 모바일 앱에 포함된 키는 완전히 안전하게 보호하기 어렵다.

하지만 이유가 보안만은 아니다.

클라이언트가 Provider를 직접 호출하면 서비스가 작업 흐름을 통제하기 어려워진다. 어떤 사용자가 어떤 입력으로 요청했는지, 이 요청이 서비스 정책에 맞는지, 사용량 제한을 넘지 않았는지, 결과가 누구의 소유인지, 실패했을 때 어떤 상태로 남겨야 하는지 서버가 일관되게 관리하기 어렵다.

AI 기능은 보통 서비스 도메인과 연결된다. 예를 들어 사용자의 권한, 구독 상태, 남은 생성 횟수, 입력 이미지의 소유권, 생성 결과의 공개 여부 같은 조건이 붙을 수 있다. 이런 판단은 Provider가 아니라 서비스가 해야 한다.

따라서 클라이언트는 외부 AI Provider를 직접 호출하는 주체가 아니라, 서비스에 “AI 작업을 요청하는 주체”로 두는 편이 안전하다. 백엔드는 이 요청을 검증하고, 서비스 기준에 맞는 작업으로 바꾼 뒤 Provider를 호출해야 한다.

## 서비스 요청과 Provider 요청은 다르다

서비스가 이해하는 요청과 Provider가 이해하는 요청은 다르다.

서비스 관점에서는 다음 정보가 중요할 수 있다.

```text
- userId
- petId
- generationType
- style
- requestSource
- quota policy
- result visibility
```

반면 Provider 관점에서는 다음 정보가 중요할 수 있다.

```text
- model
- prompt
- input image URL
- output format
- size
- seed
- callback URL
```

둘은 서로 연결되지만 같은 개념은 아니다. 서비스 요청을 그대로 Provider 요청으로 노출하면 서비스 코드가 Provider의 세부 스펙에 강하게 묶인다. 처음에는 빠르게 구현할 수 있지만, 모델을 바꾸거나 옵션을 조정하거나 Provider를 교체해야 할 때 변경 범위가 커질 수 있다.

AI 모델 호출 서버는 이 둘 사이에서 변환 역할을 한다. 사용자의 도메인 요청을 Provider가 이해할 수 있는 호출 형식으로 바꾸고, Provider 응답을 다시 서비스가 이해할 수 있는 상태와 결과로 바꾼다.

이 경계가 있으면 서비스 내부에서는 Provider의 세부 필드보다 “어떤 사용자가 어떤 AI 작업을 요청했고, 그 작업이 어떤 상태인가”를 중심으로 다룰 수 있다.

## Provider 성공과 서비스 성공은 다르다

외부 AI Provider가 성공 응답을 줬다고 해서 서비스 작업이 끝난 것은 아니다.

예를 들어 이미지 생성 작업을 생각해보면, Provider가 이미지를 생성했더라도 서비스 입장에서는 아직 해야 할 일이 남아 있을 수 있다.

```text
1. Provider에 생성 요청을 보낸다.
2. Provider가 결과를 만든다.
3. 서버가 결과 파일을 가져온다.
4. Object Storage에 저장한다.
5. Job 상태를 성공으로 갱신한다.
6. 사용자가 결과를 조회할 수 있게 한다.
```

이 흐름 중 하나라도 실패하면 사용자는 정상적으로 결과를 사용할 수 없다. Provider 호출은 성공했지만 결과 파일 다운로드에 실패할 수 있고, 파일 저장은 성공했지만 상태 업데이트에 실패할 수도 있다.

그래서 Provider 관점의 성공과 서비스 관점의 성공을 구분해야 한다. 서비스에서 성공이라고 말하려면, 사용자가 실제로 결과를 사용할 수 있는 상태까지 도달해야 한다.

이 구분이 없으면 장애 상황에서 혼란이 생긴다. Provider는 성공했다고 기록되어 있는데 사용자는 결과를 못 보거나, 결과 파일은 저장되어 있는데 Job 상태는 실패로 남는 식의 중간 상태가 생길 수 있다.

## Provider 추상화는 필요한 만큼만 한다

AI 모델 호출 서버를 만들다 보면 여러 Provider를 바꿔 끼울 수 있는 추상화를 만들고 싶어진다. 이 방향은 필요할 수 있지만, 너무 이른 시점에 모든 Provider를 하나의 완벽한 인터페이스로 일반화하려 하면 오히려 중요한 차이가 사라질 수 있다.

Provider마다 모델 옵션, 결과 제공 방식, callback 지원 여부, idempotency 지원 여부, 비용 구조, 실패 코드가 다를 수 있다. 이런 차이를 무리하게 숨기면 내부 코드는 단순해 보이지만, 실제 운영에서는 Provider별 예외를 다시 우회 처리하게 될 수 있다.

따라서 추상화의 기준은 “모든 Provider를 똑같이 보이게 하는 것”이 아니라, “서비스가 의존해야 할 작업 단위와 Provider별 구현 차이를 분리하는 것”에 두는 편이 좋다.

예를 들어 서비스는 “이미지 생성 작업을 요청한다”, “작업 결과를 저장한다”, “실패 상태를 기록한다”는 흐름에 집중하고, 특정 Provider의 prompt 형식이나 응답 필드는 adapter 쪽에 격리할 수 있다.

## 정리

외부 AI 모델 호출 서버는 Provider API를 대신 호출하는 얇은 wrapper가 아니다. 서비스 요청을 검증하고, Provider 요청으로 변환하며, Provider 결과를 서비스가 소유할 수 있는 상태로 바꾸는 경계다.

이 경계를 명확히 두면 API key 보호뿐 아니라 사용자 권한, 사용량 제한, 결과 소유권, 실패 처리, 상태 관리까지 서비스 기준으로 다룰 수 있다.

핵심은 Provider 호출 자체가 아니라, 그 호출을 서비스 내부의 작업 단위로 바꾸는 것이다. 외부 AI 작업을 안정적으로 다루려면 “Provider가 성공했는가”보다 “서비스가 사용자에게 결과를 제공할 수 있는 상태가 되었는가”를 기준으로 봐야 한다.
