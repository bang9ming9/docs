# AI Job 상태, 결과 저장, Retry를 함께 설계해야 하는 이유

## 비동기 처리 이후의 핵심은 상태다

AI 모델 호출을 비동기 Job으로 분리하면 API 요청의 timeout 부담은 줄어든다. API 서버는 Job을 생성하고 jobId를 반환하면 되고, 실제 Provider 호출은 Worker가 처리한다.

하지만 비동기 구조로 바꿨다고 해서 문제가 끝나는 것은 아니다. 오히려 이후부터는 작업 상태를 어떻게 남기고 복구할지가 더 중요해진다.

Provider 호출은 성공했지만 결과 저장이 실패할 수 있다. 결과 저장은 성공했지만 Job 상태 업데이트가 실패할 수 있다. Worker가 작업 중 죽으면 Job이 `processing` 상태로 계속 남을 수 있다. Retry가 잘못 설계되면 이미 처리 중인 작업을 다시 Provider에 요청해 중복 비용이 발생할 수도 있다.

비동기 AI 작업에서 중요한 것은 Provider를 호출하는 코드 하나가 아니라, 작업이 어디까지 진행됐는지 복구 가능한 상태로 남기는 것이다.

## Job 상태와 결과 저장은 다른 책임이다

Job 상태와 결과 파일은 서로 다른 책임을 가진다.

Job 상태는 작업의 진행 상황을 설명한다.

```text
- jobId
- userId
- status
- providerJobId
- retryCount
- errorCode
- resultObjectKey
- createdAt
- updatedAt
```

반면 Object Storage는 사용자가 실제로 소비할 산출물을 보관한다.

```text
- generated image
- generated video
- thumbnail
- metadata file
```

이 둘을 분리해서 생각해야 장애 상황을 더 명확하게 볼 수 있다.

예를 들어 Object Storage에는 결과 파일이 있는데 Job 상태가 `failed`로 남아 있다면, 결과 저장 이후 상태 갱신 단계에서 문제가 있었을 수 있다. 반대로 Job 상태는 `succeeded`인데 resultObjectKey가 없거나 실제 파일이 없다면, 성공 상태로 너무 일찍 전환했을 수 있다.

따라서 Job 상태는 단순히 Worker가 어떤 함수를 실행했는지 기록하는 값이 아니다. 사용자가 결과를 조회할 수 있는지, 운영자가 실패 지점을 추적할 수 있는지 판단하는 기준이다.

## 성공 상태는 언제 기록해야 하는가

AI Job에서 `succeeded` 상태로 전환하는 시점은 신중해야 한다.

Provider가 성공 응답을 줬다는 이유만으로 Job을 성공으로 바꾸면 안 된다. 서비스 기준의 성공은 사용자가 결과를 사용할 수 있는 상태가 되었을 때에 가깝다.

예를 들어 이미지 생성 작업이라면 다음 흐름이 끝나야 성공으로 볼 수 있다.

```text
1. Provider 호출 성공
2. Provider 결과 확인
3. 결과 파일 다운로드
4. Object Storage 업로드
5. resultObjectKey 저장
6. Job 상태 succeeded 전환
```

이 중간에 실패하면 사용자 입장에서는 결과를 사용할 수 없다. 따라서 Provider 성공과 서비스 성공을 분리해야 한다.

물론 시스템에 따라 Provider 결과 URL을 그대로 사용하는 구조도 있을 수 있다. 하지만 그 경우에도 URL 만료, 접근 권한, 재조회 가능성, 장애 복구 방식을 따로 고려해야 한다. 서비스가 결과를 장기적으로 소유해야 한다면 내부 저장소로 복사한 뒤 성공 처리하는 편이 더 명확할 수 있다.

## Retry는 무조건 재호출이 아니다

Retry는 일시 장애를 복구하기 위한 중요한 장치다. 네트워크가 잠깐 불안정하거나 Provider가 일시적으로 실패하거나 Object Storage 업로드가 실패했을 때 재시도는 도움이 된다.

하지만 AI Provider 호출에서 retry는 조심해야 한다. 같은 요청을 다시 보내는 것이 단순한 재시도가 아니라 추가 비용이나 중복 결과 생성으로 이어질 수 있기 때문이다.

특히 문제는 서버가 실패로 판단한 시점과 Provider가 실제로 작업을 처리한 시점이 다를 수 있다는 점이다.

예를 들어 서버가 timeout을 받았다고 해도 Provider가 요청을 받지 못했다고 단정할 수 없다. Provider는 이미 작업을 수락했고 결과를 생성 중일 수 있다. 이때 서버가 같은 요청을 새로 보내면 동일한 작업이 두 번 실행될 수 있다.

따라서 retry 전에 가능한 경우 다음 정보를 확인해야 한다.

```text
- providerJobId가 이미 존재하는가?
- Provider 쪽 작업 상태를 조회할 수 있는가?
- resultObjectKey가 이미 저장되어 있는가?
- 같은 입력에 대해 재사용 가능한 결과가 있는가?
- retry 횟수와 backoff 기준을 넘지 않았는가?
```

Retry는 “실패했으니 다시 호출한다”가 아니라, “현재 상태를 확인한 뒤 다시 진행해도 안전한 단계부터 이어간다”에 가까워야 한다.

## 중복 실행은 비용과 결과 불일치로 이어질 수 있다

비동기 Worker 구조에서는 중복 실행 가능성을 완전히 제거하기 어렵다.

Worker가 Job을 가져간 뒤 처리 중 죽을 수 있다. 상태 업데이트 직전에 장애가 발생할 수도 있다. Lock이나 lease가 만료되어 다른 Worker가 같은 Job을 다시 가져갈 수도 있다. 메시지 큐를 사용하는 경우에도 같은 메시지가 다시 전달될 수 있다.

이런 상황에서는 같은 Job이 두 번 처리될 수 있다고 가정하는 편이 안전하다.

AI 작업에서 중복 실행은 특히 부담이 크다. 외부 Provider 비용이 중복 발생할 수 있고, 같은 입력이어도 서로 다른 결과가 만들어질 수 있으며, 사용자가 어떤 결과를 최종 결과로 봐야 하는지 애매해질 수 있다.

중복 실행을 줄이기 위해서는 다음과 같은 기준을 둘 수 있다.

```text
- Job을 processing으로 전환할 때 atomic update를 사용한다.
- providerJobId를 저장해 이미 요청한 Provider 작업을 추적한다.
- resultObjectKey가 이미 있으면 결과를 재사용한다.
- Provider가 idempotency key를 지원하면 jobId 기반으로 활용한다.
- Worker lease가 만료된 Job은 무조건 재호출하지 않고 상태를 확인한다.
```

중요한 것은 중복 실행을 예외적인 버그로만 보지 않는 것이다. 비동기 작업 처리에서는 중복 실행이 발생할 수 있고, AI Provider 호출에서는 그 비용이 커질 수 있다.

## Stale Processing을 감지해야 한다

비동기 Job 시스템에서 자주 생기는 문제 중 하나는 Job이 `processing` 상태로 멈추는 것이다.

예를 들어 Worker가 Job을 가져간 뒤 프로세스가 죽으면 Job 상태가 그대로 남을 수 있다. Provider 호출 중 timeout이 발생했거나, 결과 저장 이후 상태 업데이트에 실패했을 때도 비슷한 상태가 생길 수 있다.

이런 Job을 그대로 두면 사용자는 계속 처리 중인 것처럼 보게 된다. 운영자도 실제로 작업이 진행 중인지, 이미 멈춘 것인지 판단하기 어렵다.

그래서 stale processing 감지가 필요하다. 일정 시간 이상 `processing` 상태로 남은 Job은 별도 기준으로 확인해야 한다.

```text
- Provider 작업 상태를 다시 조회한다.
- 결과 파일이 이미 저장되었는지 확인한다.
- 재시도 가능한 상태인지 판단한다.
- 필요하면 failed 또는 retrying 상태로 전환한다.
- 수동 복구가 필요한 경우 운영 로그를 남긴다.
```

여기서도 중요한 것은 무조건 새 Provider 요청을 보내지 않는 것이다. 이미 Provider 쪽에서 결과가 만들어졌을 수 있으므로, 재호출 전에 기존 작업과 결과를 확인하는 흐름이 필요하다.

## 실패 정보는 복구 가능한 형태로 남겨야 한다

실패를 단순히 문자열 메시지로만 남기면 나중에 복구하기 어렵다. 운영자는 실패가 어떤 단계에서 발생했는지, 재시도 가능한지, 사용자에게 어떤 안내를 해야 하는지 알아야 한다.

가능하면 실패 정보는 구조화해서 남기는 편이 좋다.

```text
- errorCode
- errorMessage
- failedStep
- providerStatusCode
- retryable
- retryCount
- lastAttemptAt
```

특히 `failedStep`은 유용하다. 실패가 Provider 호출 단계인지, 결과 다운로드 단계인지, Object Storage 업로드 단계인지, 상태 업데이트 단계인지에 따라 대응 방식이 달라지기 때문이다.

같은 `failed` 상태라도 원인은 다를 수 있다. 이 차이를 남겨야 retry, 사용자 안내, 운영 복구를 안전하게 할 수 있다.

## 정리

AI Job 처리는 Provider 호출 하나로 끝나지 않는다. 작업 생성, Provider 호출, 결과 확인, 저장소 업로드, 상태 갱신, 사용자 조회까지 이어지는 흐름이다. 이 중 어느 단계에서든 실패할 수 있고, 일부 단계만 성공한 중간 상태도 생길 수 있다.

그래서 Job 상태, 결과 저장, Retry를 함께 설계해야 한다. Provider 성공을 서비스 성공으로 바로 보지 말고, 사용자가 결과를 사용할 수 있는 상태까지 도달했는지 확인해야 한다.

Retry도 단순 재호출이 아니다. 현재 Job 상태, providerJobId, resultObjectKey, retry 횟수, 실패 단계를 보고 다시 진행할 수 있는 위치를 판단해야 한다.

핵심은 다음과 같다.

> 비동기 AI 작업에서 중요한 것은 Provider를 한 번 호출하는 코드가 아니라, 작업이 어디까지 진행됐는지 복구 가능한 상태로 남기는 것이다.
