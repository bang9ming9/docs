# Go에서 `fasthttp`를 어떻게 이해하면 좋을까

Go 서버 코드를 보다 보면 `fasthttp`라는 이름을 꽤 자주 마주친다. 처음에는 `HTTP/1.1`, `HTTP/2`처럼 HTTP 표준의 또 다른 계층이나 프로토콜 이름처럼 느껴지기도 한다. 이름 자체가 `fast + http` 조합이라서, “더 빠른 HTTP 표준이 따로 있나?”라는 오해가 생기기 쉽다.

이 메모는 그 헷갈림을 정리하는 데 목적이 있다. 핵심은 단순하다. **`fasthttp`는 새로운 HTTP 표준 프로토콜이 아니라, Go에서 HTTP를 처리하기 위한 성능 지향 라이브러리(구현체)에 가깝다.**

## 1) 왜 이름만 보면 HTTP의 다른 표준처럼 느껴질까

오해가 생기는 이유는 자연스럽다.

- 이름에 `http`가 직접 들어간다.
- `fast`라는 수식이 붙어 “기존 HTTP보다 진화한 무언가”처럼 읽히기 쉽다.
- 실무 문맥에서 “`net/http` 대신 `fasthttp`” 같은 표현을 보면, 표준의 세대 교체처럼 보일 수 있다.

하지만 HTTP 표준 자체는 IETF 문서(RFC)로 정의되는 언어 독립적인 규약이다. 어떤 언어에서 어떤 라이브러리로 서버를 구현하느냐와는 계층이 다르다. 이 구분을 먼저 잡아두면 이후 판단이 훨씬 편해진다.

## 2) 실제로 `fasthttp`는 무엇인가

`fasthttp`는 Go 생태계 안에서 HTTP 서버/클라이언트 처리 경로를 성능 중심으로 구현한 라이브러리다.

- 프로토콜을 새로 정의하는 도구가 아니라,
- Go 런타임 위에서 HTTP 요청/응답 처리 방식을 다르게 설계한 구현이다.

즉, 비교 축은 보통 “HTTP 표준 vs `fasthttp`”가 아니라 “Go의 표준 `net/http` 구현 vs `fasthttp` 구현”에 가깝다.

여기서 중요한 점은 `fasthttp`를 `net/http`의 상위호환으로 이해하면 곤란하다는 것이다. 설계 우선순위가 다르고, API/호환성/생태계 연결성에서도 차이가 있기 때문에 “더 새로운 것”보다는 “성격이 다른 선택지”로 보는 편이 정확하다.

## 3) 왜 `net/http` 외에 이런 구현이 따로 존재할까

이 질문은 “왜 표준 라이브러리 하나로 끝나지 않았는가”에 대한 이야기다. 보통 이유는 다음처럼 정리할 수 있다.

- 어떤 서비스는 매우 높은 처리량과 짧은 지연 시간에 민감하다.
- 이런 구간에서는 메모리 할당 패턴, 객체 재사용, 파싱/직렬화 경로 같은 구현 세부가 체감 성능에 영향을 준다.
- 표준 라이브러리는 범용성·안정성·호환성을 넓게 고려하는 반면, 특정 라이브러리는 더 좁은 목표(성능)에 우선순위를 둘 수 있다.

`fasthttp`의 존재 이유도 이 맥락에서 이해하는 게 좋다. “표준이 틀렸기 때문”이 아니라, **성능 지향 목표를 위해 다른 트레이드오프를 택한 구현이 필요했던 것**에 가깝다.

## 4) “성능 지향 설계”는 어떻게 이해해야 할까

성능 지향이라는 말은 “어떤 상황에서도 항상 더 빠르다”는 선언이 아니다. 보통은 아래와 같은 의미에 가깝다.

- 요청 처리 경로에서 불필요한 비용을 줄이려는 설계,
- 메모리 할당과 GC 부담을 줄이려는 선택,
- API 사용 방식에도 성능 관점을 반영한 인터페이스.

이런 선택은 특정 워크로드에서 유리할 수 있다. 하지만 실무 성능은 네트워크, 비즈니스 로직, DB/캐시 I/O, 직렬화 포맷, 배포 환경, 운영 패턴이 함께 결정한다. 그래서 라이브러리 벤치마크 숫자만으로 실제 서비스 전체 성능을 일반화하기는 어렵다.

정리하면, `fasthttp`의 포인트는 “무조건 더 빠른 정답”이 아니라 “성능을 위해 어떤 제약과 설계를 채택했는지 이해할 수 있는 구현”이라는 쪽에 있다.

## 5) 실무에서는 어떤 관점으로 받아들이면 좋을까

실무에서는 아래 정도의 기대치가 현실적이다.

1. **도구의 계층을 먼저 분리해서 이해한다.**
   - HTTP 표준(언어 독립)과 Go 라이브러리 선택(언어 내부 구현)을 섞지 않는다.

2. **벤치마크는 출발점으로만 사용한다.**
   - “숫자가 높다”보다 “우리 트래픽/핫패스/병목에서 어떤 이득이 나는가”를 본다.

3. **적용 비용과 운영 맥락을 함께 본다.**
   - 기존 코드, 팀의 익숙함, 미들웨어/라이브러리 호환성, 디버깅/관측 가능성까지 포함해서 판단한다.

4. **평가 단위를 서비스 수준으로 둔다.**
   - 프레임워크/라이브러리 단위 마이크로 벤치마크보다, 실제 API 시나리오 부하 테스트와 운영 지표(지연 분포, 에러율, 리소스 사용량)로 검증한다.

이렇게 보면 `fasthttp`는 “채택하면 자동으로 이득이 나는 기술”이 아니라, **명확한 목적과 측정 계획이 있을 때 검토할 수 있는 성능 지향 옵션**으로 자리 잡는다.

## 6) 짧은 결론

- `fasthttp`는 HTTP/1.1, HTTP/2 같은 표준 프로토콜의 대안이 아니다.
- `fasthttp`는 Go에서 HTTP 처리를 구현하는 성능 지향 라이브러리다.
- 핵심은 “항상 더 빠른가”가 아니라, 왜 이런 구현이 존재하는지와 어떤 트레이드오프를 택했는지를 이해하는 데 있다.
- 실무에서는 벤치마크 수치를 그대로 일반화하지 말고, 적용 맥락과 기대치를 함께 검증하는 접근이 안전하다.
