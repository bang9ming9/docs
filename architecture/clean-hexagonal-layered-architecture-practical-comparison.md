# 클린 아키텍처, 헥사고날, 레이어드 아키텍처를 어떻게 구분할까

## 1) 문제 배경
최근 프로젝트를 클린 아키텍처로 구성하다 보면, “이게 헥사고날이랑 뭐가 다르지?”라는 질문이 자주 나온다. 특히 Go 백엔드에서 `handler`, `usecase`, `repository`, `adapter`를 나누기 시작하면 두 구조가 코드 레벨에서는 꽤 비슷하게 보인다.

여기에 DDD까지 함께 언급되면 더 헷갈리기 쉽다. 다만 DDD는 레이어드/헥사고날/클린처럼 시스템의 **구조 형태**를 직접 규정하는 아키텍처라기보다, 복잡한 도메인 규칙을 모델링하고 언어를 맞추기 위한 **설계 접근**에 가깝다. 이 글에서는 DDD 자체를 깊게 다루기보다, 실무에서 자주 비교되는 세 가지 아키텍처의 차이를 중심으로 정리한다.

## 2) 레이어드 아키텍처
레이어드 아키텍처는 보통 다음 흐름으로 이해한다.

- `handler/controller` → `service` → `repository` → `database`

요청이 들어오면 상위 계층에서 하위 계층으로 내려가며 처리하는 구조다. 팀에 처음 합류한 사람도 호출 흐름을 읽기 쉬운 편이고, CRUD 중심 서비스에서는 구현 비용이 비교적 낮다.

### 장점
- 코드 흐름이 직관적이다.
- 역할 분리가 단순해서 온보딩이 빠르다.
- 단순 업무 시스템이나 초기 MVP에서 생산성이 좋을 수 있다.

### 단점
- 서비스가 커지면 `service` 계층이 비대해지기 쉽다.
- 비즈니스 로직이 `repository`나 DB 모델 제약에 끌려가는 일이 생길 수 있다.
- 테스트가 DB/프레임워크에 묶이면 빠른 피드백 루프를 만들기 어렵다.

중요한 점은, 레이어드가 “항상 나쁜 구조”는 아니라는 것이다. 단순하고 변경 폭이 작은 서비스에서는 여전히 실용적인 선택이 될 수 있다.

## 3) 헥사고날 아키텍처 (Ports and Adapters)
헥사고날 아키텍처의 핵심은 내부 애플리케이션/도메인 로직과 외부 시스템을 분리하는 데 있다. HTTP, DB, 메시지 브로커, 외부 API 같은 기술 요소는 **Adapter**로 보고, 내부는 **Port(인터페이스)**를 통해 필요한 능력만 바라본다.

예를 들어 Go에서 주문 저장이 필요하다고 하면 내부는 다음처럼 포트를 정의할 수 있다.

```go
type OrderRepository interface {
    Save(ctx context.Context, order Order) error
    FindByID(ctx context.Context, id string) (Order, error)
}
```

그리고 외부 기술 구현체는 어댑터로 분리한다.

```go
type MySQLOrderRepository struct {
    db *sql.DB
}
```

이 구조에서는 use case가 `MySQL` 자체를 직접 알 필요가 없다. 필요한 것은 `OrderRepository`라는 계약이다.

### 장점
- 외부 기술 교체(MySQL→다른 저장소, HTTP→gRPC)에 상대적으로 유연하다.
- 테스트에서 어댑터를 목/페이크로 바꿔 격리하기 쉽다.

### 단점
- 포트/인터페이스가 늘어나면 구조가 무거워질 수 있다.
- 작은 프로젝트에서는 초기 설계 비용이 과하게 느껴질 수 있다.

## 4) 클린 아키텍처
클린 아키텍처는 보통 다음 계층과 의존성 규칙으로 설명한다.

- **Entity**
- **Use Case**
- **Interface Adapter**
- **Framework/Driver**

핵심은 의존성이 항상 안쪽(비즈니스 규칙)으로 향해야 한다는 점이다. 즉, `UseCase`는 DB 드라이버, HTTP 프레임워크, 메시지 브로커 같은 구체 기술을 직접 알지 않는다.

왜 이렇게 하느냐면, 핵심 정책(비즈니스 규칙)이 외부 기술 변화에 덜 흔들리게 하기 위해서다. 예를 들어 웹 프레임워크를 바꾸거나 저장소가 바뀌어도, `UseCase`가 안정적으로 유지되면 영향 범위를 줄일 수 있다.

다만 복잡도가 낮은 CRUD 서비스에 동일한 수준으로 적용하면 파일 수와 추상화가 급격히 늘어날 수 있다. 즉, 클린 아키텍처의 장점은 주로 “변경 가능성과 테스트 가능성의 가치가 큰 상황”에서 더 분명해진다.

## 5) 세 아키텍처의 차이
| 비교 기준 | 레이어드 | 헥사고날 | 클린 |
|---|---|---|---|
| 핵심 관심사 | 계층적 분리와 호출 흐름 | 내부 로직과 외부 시스템 경계 | 비즈니스 규칙 중심 + 의존성 규칙 |
| 코드 흐름 | 상위→하위 계층 호출 | 유스케이스가 포트를 통해 외부 접근 | 바깥 계층이 안쪽 유스케이스를 호출 |
| 의존성 방향 | 보통 위→아래(구현 의존이 섞이기 쉬움) | 내부는 포트에 의존, 어댑터가 구현 | 모든 의존성이 안쪽을 향함 |
| 외부 시스템과의 경계 | 상대적으로 약할 수 있음 | 포트/어댑터로 명확히 분리 | 어댑터 계층으로 명확히 분리 |
| 초기 이해 난이도 | 낮은 편 | 중간~높음 | 중간~높음 |
| 테스트 격리 | 구조에 따라 편차 큼 | 좋은 편(어댑터 교체 용이) | 좋은 편(유스케이스 중심 테스트) |
| 적합한 상황 | 단순 CRUD, 빠른 개발 | 외부 의존성 다양, 교체/격리 필요 | 복잡 규칙, 장기 유지보수, 테스트 중요 |

실무에서 체감되는 차이는 주로 초기 비용에서 나온다. 레이어드는 빨리 이해하고 만들 수 있고, 클린/헥사고날은 초반에 구조를 이해하고 맞추는 비용이 더 든다. 대신 후자는 장기적으로 외부 의존성과 핵심 로직을 분리하는 데 이점이 있을 수 있다.

## 6) 클린 아키텍처와 헥사고날 아키텍처의 관계
두 아키텍처는 완전히 반대되는 선택지라기보다, 내부 비즈니스 로직을 외부 기술에서 보호하려는 공통 방향을 가진다.

- 헥사고날: **Port/Adapter 경계**를 강조
- 클린: **계층과 의존성 규칙**을 더 명시적으로 설명

그래서 실제 프로젝트에서는 용어와 폴더 구조가 혼합되어 쓰이는 경우가 많다. 예를 들어 “클린 아키텍처 기반인데 repository port/adapter를 둔다” 같은 식이다.

## 7) 실무적인 선택 기준
아키텍처 선택은 정답 고르기가 아니라, 프로젝트 복잡도와 변경 가능성에 맞춰 비용을 지불하는 결정에 가깝다.

- 단순 CRUD와 빠른 개발이 핵심이면 레이어드로도 충분할 수 있다.
- 외부 API/DB/메시지 브로커 의존성이 많고 교체 가능성, 테스트 격리가 중요하면 헥사고날/클린 방식이 유리할 수 있다.
- 도메인 규칙이 복잡하고 오래 유지해야 한다면 `UseCase`/`Domain` 중심 구조가 도움이 된다.
- 모든 기능에 같은 수준의 추상화를 강제하기보다, 변경 가능성이 높은 경계와 핵심 로직부터 점진적으로 적용하는 편이 현실적이다.

예를 들어 Go 서비스에서 처음엔 `handler-service-repository`로 시작하되, 결제/정산처럼 규칙이 복잡한 영역부터 `usecase + port/adapter`로 분리하는 방식도 가능하다.

## 8) 짧은 결론
이름보다 중요한 질문은 이것이다.

> 핵심 비즈니스 로직이 외부 기술(프레임워크, DB, 메시지 브로커)에 끌려가고 있지 않은가?

레이어드는 단순성과 직관성이 장점이고, 클린/헥사고날은 변경 대응과 테스트를 위해 복잡성을 감수하는 구조다. 어느 하나를 정답으로 두기보다, 현재 프로젝트의 복잡도와 변경 가능성에 맞춰 선택하고 조정하는 것이 실무적으로 더 안전하다.
