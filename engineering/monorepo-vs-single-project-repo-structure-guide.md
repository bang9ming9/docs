# 모노레포 vs 일반 단일 프로젝트: 저장소 구조를 실무에서 어떻게 판단할까

저장소 구조를 정할 때 자주 나오는 질문이 있다. “지금 모노레포로 가야 하나, 아니면 일반 단일 프로젝트를 유지해야 하나?”

헷갈리는 이유는 단순하다. 둘 다 실제로 성공 사례가 있고, 팀/제품 단계/운영 방식에 따라 유리한 지점이 다르기 때문이다. 어떤 조직에서는 모노레포가 협업 속도를 높여주지만, 다른 조직에서는 오히려 CI 부담과 권한 관리 복잡도만 키울 수 있다.

이 문서는 “무엇이 정답인가”를 말하기보다, **저장소 구조 관점에서 어떤 조건에서 어떤 선택이 자연스러운지**를 실무적으로 정리한다.

## 이 글에서 말하는 모노레포의 의미

여기서 말하는 모노레포는 다음처럼 **여러 앱, 서비스, 워커, 공통 모듈을 하나의 저장소에서 함께 관리**하는 구성을 뜻한다.

- 웹/모바일 백엔드 API 서비스
- 배치/비동기 워커
- 공통 라이브러리(도메인 로직, 유틸, SDK)
- 공통 계약(protobuf, OpenAPI, shared package)
- 빌드/테스트/린트/배포 관련 공통 툴링 설정

반대로 일반 단일 프로젝트는 하나의 제품 또는 서비스 단위를 중심으로 저장소가 분리되어 있고, 다른 프로젝트와는 별도 저장소로 운영되는 구성을 가리킨다.

핵심은 기술 스택보다 **저장소 경계가 어디에 그어져 있느냐**다.

## 모노레포의 장점과 단점

### 장점

1. **공통 코드 관리가 쉬워진다**  
   여러 프로젝트가 같은 유틸/도메인 모듈/클라이언트를 쓸 때, 하나의 저장소에서 변경과 리뷰를 함께 관리할 수 있다. 중복 구현을 줄이고 공통 자산의 재사용 흐름을 만들기 쉽다.

2. **여러 애플리케이션·모듈의 동시 변경 추적이 유리하다**  
   예를 들어 API 계약 변경, 공통 인증 로직 수정처럼 여러 영역을 함께 바꿔야 하는 작업에서 변경 히스토리를 한 곳에서 따라가기 쉽다. 이력 파편화가 줄어들어 “왜 이 변경이 필요했는지” 맥락을 보존하기 좋다.

3. **내부 라이브러리 버전 관리 부담이 줄어든다**  
   별도 저장소 기반에서는 내부 패키지 릴리스/버전 업그레이드/호환성 조정이 반복되기 쉽다. 모노레포에서는 같은 커밋에서 소비자와 제공자를 함께 조정하는 방식이 가능해, 내부 버전 맞추기 비용이 줄어드는 편이다.

4. **개발 규칙과 툴링을 통일하기 쉽다**  
   린트 규칙, 테스트 실행 방식, 코드 생성 파이프라인, CI 규칙을 저장소 수준에서 정리하기 쉬워진다. 팀이 커질수록 “기본 규칙의 일관성” 자체가 생산성에 영향을 주는 경우가 많다.

### 단점

1. **저장소와 CI가 무거워질 수 있다**  
   프로젝트 수가 늘어나면 체크아웃 크기, 빌드 시간, 테스트 범위, 캐시 전략이 빠르게 복잡해진다. 변경 영향 범위를 잘 제어하지 못하면 작은 수정에도 과도한 파이프라인이 돌 수 있다.

2. **설계를 잘못하면 결합도가 높아질 수 있다**  
   “한 저장소에 있으니 쉽게 참조하자”가 누적되면 경계가 흐려질 수 있다. 공통화가 아니라 의존성 확산이 되면, 결과적으로 독립 배포와 책임 분리가 어려워질 수 있다.

3. **권한·소유권·배포 파이프라인 관리가 복잡해질 수 있다**  
   팀별 코드 오너십, 민감 코드 접근 제어, 서비스별 배포 책임이 다를 때 하나의 저장소 안에서 정책을 세분화해야 한다. 기술적으로 가능해도 운영 체계 설계가 따라오지 않으면 마찰이 생긴다.

## 일반 단일 프로젝트의 장점과 단점

### 장점

1. **단순하다**  
   저장소 구조, CI 설정, 권한 모델이 상대적으로 직관적이다. 초기 단계에서는 이 단순함이 가장 큰 장점이 되기도 한다.

2. **독립성이 높다**  
   프로젝트 간 의존이 저장소 차원에서 강제되지 않아, 각 팀이 릴리스 주기와 기술 선택을 독립적으로 가져가기 쉽다.

3. **배포 단위가 명확하다**  
   저장소와 배포 대상이 거의 1:1로 대응되기 때문에 책임 경계가 분명하다. 장애 대응이나 변경 롤백에서도 의사결정이 단순해지는 경우가 많다.

### 단점

1. **공통 코드 관리 비용이 커질 수 있다**  
   공통 로직이 늘어나면 공유 방식(복사, 내부 패키지, 별도 라이브러리 저장소)마다 운영 비용이 생긴다. 특히 여러 저장소에서 동시 개선이 필요할 때 반복 작업이 많아진다.

2. **여러 프로젝트를 함께 바꿔야 할 때 불편하다**  
   공통 계약 변경이나 횡단 기능 개선에서 저장소별 PR/릴리스/배포를 맞춰야 하므로 조정 비용이 커질 수 있다.

## 어떤 상황에서 무엇이 더 잘 맞을까

아래 기준은 절대 규칙이 아니라, 저장소 구조 선택 시 자주 쓰이는 실무적 신호다.

### 모노레포가 잘 맞는 상황

- **여러 앱/서비스/워커/공통 모듈이 함께 자주 바뀐다.**  
  동시 변경이 일상이라면 한 저장소에서 원자적으로 다루는 방식이 협업 비용을 줄일 수 있다.

- **공통 계약의 중요도가 높다.**  
  protobuf, OpenAPI, shared package 같은 계약 자산이 핵심이면, 계약 변경과 소비 코드 변경을 함께 추적하는 구조가 안정적일 때가 많다.

- **툴링과 규칙 운영을 감당할 수 있다.**  
  변경 영향 분석, 선택적 CI, 캐시 전략, 코드 오너십 정책 같은 운영 장치를 유지할 역량이 있다면 모노레포의 장점을 살리기 쉽다.

### 일반 단일 프로젝트가 더 적합한 상황

- **아직 서비스가 하나뿐이다.**  
  공유 자산보다 제품 자체 속도가 더 중요할 수 있고, 저장소를 크게 설계할 유인이 약할 수 있다.

- **공통화할 대상이 아직 불명확하다.**  
  도메인 경계와 재사용 패턴이 안정되지 않은 시점이라면, 성급한 통합보다 명확한 분리가 학습 비용을 줄일 때가 있다.

- **팀/권한/배포 경계가 특히 중요하다.**  
  조직 구조상 강한 분리와 독립 배포가 핵심이라면, 저장소 분리가 운영 정책과 더 잘 맞을 수 있다.

## 실무에서 판단할 때 체크할 기준

결정을 단순화하려면 “좋다/나쁘다” 대신 다음 질문에 답해보는 편이 유용하다.

1. **같이 바뀌는가?**  
   서로 다른 프로젝트가 한 요구사항 때문에 동시 수정되는 빈도가 높은지 본다. 동시 변경이 잦다면 모노레포 쪽 이점이 커질 수 있다.

2. **공통 자산이 실제로 중요한가?**  
   공통 라이브러리, 계약 스키마, 코드 생성 파이프라인이 제품 품질과 개발 속도에 실질적 영향을 주는지 확인한다.

3. **배포 단위가 독립적인가?**  
   배포/롤백/장애 대응을 프로젝트별로 분리해야 하는 요구가 강한지 본다. 독립성이 핵심이면 일반 단일 프로젝트가 더 관리하기 쉬울 수 있다.

4. **팀 구조와 맞는가?**  
   협업 방식(플랫폼 중심 vs 서비스 자율 중심), 코드 오너십, 리뷰 체계가 저장소 구조와 자연스럽게 맞물리는지 점검한다.

5. **툴링 비용을 감당할 수 있는가?**  
   특히 모노레포는 CI 최적화와 의존성 경계 관리가 품질을 좌우한다. 이를 운영할 시간과 책임 주체가 있는지 현실적으로 확인해야 한다.

## 짧은 결론

모노레포와 일반 단일 프로젝트는 우열 관계라기보다, **변경 패턴·공통 자산·배포 경계·팀 운영 방식**에 따라 유리한 지점이 달라지는 선택지다.

- 함께 자주 바뀌고 공통 계약이 중요하면 모노레포가 자연스러울 수 있다.
- 독립 배포와 명확한 경계가 더 중요하면 일반 단일 프로젝트가 더 단순하고 안정적으로 작동할 수 있다.

결국 핵심은 구조 자체가 아니라, 그 구조가 현재 팀의 실제 작업 흐름과 얼마나 맞는지다. 저장소 구조는 한 번 정하면 끝나는 결정이 아니라, 제품과 조직의 변화에 맞춰 주기적으로 다시 점검해야 하는 운영 설계에 가깝다.
