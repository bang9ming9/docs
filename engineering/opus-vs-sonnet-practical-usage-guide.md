# Opus와 Sonnet, 실무에서 어떻게 나눠 이해하고 쓸 것인가

## 왜 이 주제를 다시 꺼내야 하는가

모델 선택 이야기는 자주 비용 비교나 성능 체감으로만 흘러간다. 그래서 실무에서는 두 가지 극단이 반복된다. “단가가 낮으니 Sonnet으로 통일하자” 혹은 “중요한 일인데 Opus로만 가자” 같은 선택이다. 둘 다 이해 가능한 결정이지만, 실제 운영에서는 이렇게 단일 원칙으로 밀어붙일수록 비효율이 커지기 쉬운 구간이 생긴다.

문제는 모델 자체의 우열보다 작업의 성격이 계속 바뀐다는 데 있다. 같은 프로젝트 안에서도 어떤 단계는 해석과 판단이 중심이고, 어떤 단계는 이미 정해진 기준을 빠르게 실행하는 것이 중심이다. 이 차이를 무시하면, 싸게 시작해도 반복 수정 비용이 커지거나, 반대로 품질을 높이겠다고 과한 단가를 계속 지불하게 된다.

이 글은 “무엇이 더 좋다”를 말하려는 글이 아니다. 실무에서 왜 Sonnet 고집과 Opus 고집이 각각 생기는지 배경을 짚고, 어떤 구간에서 어떤 선택이 합리적인지 판단 기준을 정리해 보려는 글이다.

## 성능표보다 중요한 실무 체감: 판단 밀도와 실행 밀도

Opus와 Sonnet의 차이는 벤치마크 숫자로만 보면 실무 의사결정에 바로 연결되기 어렵다. 더 유용한 기준은 해당 작업이 요구하는 **판단 밀도**와 **실행 밀도**다.

판단 밀도가 높은 구간은 대체로 이런 특징을 가진다. 요구사항이 애매하고, 성공 기준이 아직 합의되지 않았고, 트레이드오프를 선택해야 하며, 반례를 먼저 찾아야 안전해진다. 예를 들면 초기 문제 정의, 설계 기준 수립, 우선순위 충돌 해소, 최종 검증 프레임 점검 같은 단계다. 이런 구간에서는 단순히 문장을 잘 생성하는 능력보다, 맥락을 엮고 기준을 세우며 판단 과정을 점검하는 능력이 실제 결과 차이에 더 크게 작용하는 경우가 많다.

이때 Opus가 의미를 갖는 이유는 “더 똑똑하다”는 추상적 표현 때문이 아니다. 애매한 상황에서 선택 근거를 구조화하고, 기준을 명시하고, 반례를 통해 계획의 취약점을 점검하는 과정을 더 안정적으로 도와주는 경우가 있기 때문이다. 특히 실패 비용이 큰 영역에서는 앞단 판단의 질이 전체 비용 구조에 미치는 영향이 커져, 이 구간의 투자 단가가 합리화되는 경우가 적지 않다.

반대로 실행 밀도가 높은 구간은 성격이 다르다. 기준과 제약이 이미 정리되어 있고, 해야 할 출력 형태가 구조화되어 있으며, 반복 수정과 계획 추종이 주된 과업이 된다. 구현 전개, 문서 포맷 정리, 템플릿 기반 산출, 정해진 규칙 안에서의 반복 보정이 여기에 가깝다.

이 구간에서는 Sonnet의 ROI가 좋아지는 경우가 많다. 핵심 해석보다 실행량과 일관성이 더 중요한 과업에서는, 요구 품질을 충족한 채 단가를 낮출 수 있는 경우가 많다. 반복량이 큰 팀일수록 단가 차이가 누적되어 운영 효율에 미치는 영향이 커지는 경향도 자주 관찰된다.

## 왜 Sonnet만 고집하는 선택이 흔들릴 수 있는가

Sonnet 중심 운영은 비용 통제 관점에서 매우 매력적이다. 실제로 요구사항이 비교적 정리된 실행 구간에서는 좋은 선택이다. 다만 한계는, 해석이 필요한 앞단까지 같은 방식으로 밀어붙일 때 드러난다.

요구사항이 애매한데도 실행 중심으로만 진행하면, 초기에 잡은 기준의 오류가 뒤 단계 전체 품질을 흔들 수 있다. 겉으로는 빠르게 진척되는 것처럼 보여도, 기준이 틀린 상태에서 반복 수정이 늘어나면 후속 단계의 누적 비용이 예상보다 커질 수 있다. 즉, “처리 속도”는 빨랐지만 “방향 정확도”가 낮아져 전체 리드타임이 길어지는 패턴이 나타나기도 한다.

여기서 중요한 점은 Sonnet이 부족해서가 아니다. 문제 성격이 이미 판단 중심으로 넘어갔는데도 실행 모델만으로 해결하려는 운영 방식이 어긋난 것이다. 모델 선택의 실패라기보다, 단계 인식의 실패에 가깝다.

## 왜 Opus만 고집하는 선택도 비효율이 될 수 있는가

Opus 중심 운영은 품질 리스크를 낮추고 싶을 때 자연스러운 반응이다. 특히 실패 비용이 큰 업무에서는 타당한 선택이 될 수 있다. 그러나 모든 단계를 동일하게 Opus로 처리하면, 기준이 이미 정리된 이후에도 높은 단가를 계속 지불하게 된다.

실행 단계의 핵심은 대개 정교한 해석이 아니라 반복 처리량과 일관성이다. 이 구간에서 더 강한 판단 능력이 더 좋은 결과로 이어지는 경우도 있지만, 항상 비례하지는 않는다. 특히 반복량이 큰 환경이나 대량 실행이 많은 워크플로에서는 같은 예산에서 처리 가능한 총량이 줄어들고, 팀 운영 관점에서 병목이 생길 가능성도 함께 커진다.

즉 “중요한 작업이니 최고 성능 모델만”이라는 원칙은 안전해 보이지만, 문제의 핵심이 정리된 뒤에는 과투자일 수 있다. 품질을 지키는 것과 모든 구간에 같은 단가를 적용하는 것은 다른 문제다.

## “Opus로 생각하고 Sonnet으로 실행한다” 전략의 의미와 한계

이 문장은 실무에서 자주 쓰이고, 많은 경우 유효하다. 특히 앞단에서 기준·제약·검증 조건이 충분히 정리되어 있고, 뒤 단계가 구조화된 실행 중심일 때는 합리적인 전략이다. 판단 비용이 큰 구간에만 고단가를 쓰고, 반복량이 큰 구간은 저단가로 전환해 전체 효율을 높일 수 있기 때문이다.

하지만 이 문장을 공식처럼 쓰면 오히려 위험하다. 뒤 단계가 겉보기에는 실행처럼 보여도, 실제로는 계속 해석이 필요한 경우가 많다. 예를 들어 예외 케이스가 반복적으로 발견되거나, 우선순위가 수시로 바뀌거나, 숨은 제약이 작업 중간에 드러나는 상황에서는 실행 단계에서도 판단 밀도가 다시 올라간다.

그래서 “plan이 잘 되어 있다”와 “이후 단계에서 판단이 사라졌다”는 같은 말이 아니다. 계획 문서는 순서를 정리해 줄 수 있지만, 현실의 변동성까지 제거해 주지는 않는다. 실행 중에도 판단 요구가 다시 커지면, 구간별로 모델 배치를 재조정해야 한다.

## 실무에서 바로 쓰는 판단 기준

모델을 고정하지 말고, 아래 질문으로 현재 작업의 성격을 점검하는 편이 안정적이다.

먼저 지금 하는 일이 생각 중심인지 실행 중심인지 본다. 해석·기준 설정·반례 검토가 핵심이면 Opus 비중이 올라가고, 이미 확정된 기준을 반복 수행하는 단계면 Sonnet 비중이 올라간다.

다음으로 실패 비용을 본다. 잘못된 초기 판단이 큰 재작업이나 운영 리스크로 이어지는 업무는 앞단 판단 품질에 더 투자할 이유가 있다. 반대로 실패 비용이 낮고 빠른 반복으로 보정 가능한 작업은 Sonnet 중심 운영이 합리적이다.

요구사항의 명확성도 중요하다. 요구가 애매할수록 해석 비용이 커지고, 명확할수록 실행 비용이 중심이 된다. 결과물 자체보다 중간 판단의 질이 더 중요한 과업인지도 같이 봐야 한다. 설계 의사결정 문서, 정책 기준 수립, 위험 검토처럼 중간 판단이 산출물 품질을 좌우하는 작업은 앞단 모델 선택이 특히 중요하다.

마지막으로 반복량을 본다. 처리 건수가 많고 구조가 유사할수록 단가 차이는 빠르게 누적된다. 이때는 기준을 충분히 고정한 뒤 실행 구간을 Sonnet으로 넘기는 편이 전체 워크플로 효율을 높이는 경우가 많다.

## 마무리: 모델 찬반보다 작업 단계 인식이 먼저다

실무에서 필요한 것은 “무조건 Sonnet”도 “무조건 Opus”도 아니다. 더 중요한 것은 지금의 과업이 판단 밀도 높은 단계인지, 실행 밀도 높은 단계인지 구분하는 능력이다.

요약하면, 애매한 문제를 해석하고 기준을 세우는 앞단에서는 Opus의 비용을 감수할 이유가 생긴다. 반대로 기준이 충분히 정리된 뒤의 반복 실행 구간에서는 Sonnet 쪽이 비용 대비 효율 면에서 유리해지는 경우가 많다. 핵심은 모델 선호가 아니라, 단계별로 어떤 비용을 지불해야 전체 품질과 속도를 함께 지킬 수 있는지 판단하는 운영 감각이다.
