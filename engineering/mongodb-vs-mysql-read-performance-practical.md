# MongoDB vs MySQL 조회 성능, 왜 논쟁이 반복되고 어디서 실제 차이가 나는가

실무에서 “MongoDB가 MySQL보다 조회가 빠르다”는 이야기는 자주 반복된다. 그런데 대부분은 **서로 다른 전제를 섞어서 비교**한 경우가 많다. 이 글은 단순 우열이 아니라, 어떤 조건에서 어떤 선택이 유리해지는지 정리한다.

## 왜 “조인 없는 단순 조회면 MongoDB가 더 빠르다”는 말이 자주 나올까

이 말이 나오는 배경은 보통 다음과 같다.

- API 응답 형태와 비슷하게 문서를 저장해 두고, `_id`나 단일 인덱스로 한 번에 조회한다.
- 여러 테이블 조인을 피하고, 애플리케이션이 바로 내려줄 수 있는 구조를 사용한다.
- 읽기 경로에서 SQL 작성/최적화보다 문서 단위 조회가 단순해 보인다.

즉, “MongoDB 자체가 항상 빠르다”라기보다, **비교 대상이 이미 MongoDB에 유리한 모델링**인 경우가 많다. 반대로 MySQL에서도 조인을 줄이고 인덱스를 맞춘 단순 조회라면 충분히 빠를 수 있다.

## 실제 성능을 더 크게 가르는 것은 DB 종류보다 설계다

조회 지연 시간은 대체로 아래 요소의 영향이 더 크다.

- 데이터 모델이 조회 패턴과 맞는가
- 인덱스가 쿼리 조건/정렬/페이지네이션 방식과 맞는가
- 쿼리 패턴이 일관적인가(핫패스 vs 자유 검색)
- 응답 형태를 만들기 위해 DB 밖에서 추가 결합/가공이 필요한가
- 네트워크 왕복, 직렬화 비용, 캐시 전략이 적절한가

같은 MongoDB라도 모델링/인덱스가 어긋나면 느리고, 같은 MySQL이라도 쿼리 패턴과 인덱스가 잘 맞으면 매우 안정적으로 빠르다. 실무에서는 엔진 이름보다 **“주요 API 95퍼센타일 지연 시간”을 만드는 경로**를 먼저 본다.

## 언제 MongoDB가 유리해질 수 있나

아래 조건에서는 MongoDB가 특히 잘 맞는 편이다.

1. **응답 단위가 문서 단위와 거의 동일할 때**
   - 예: 게시글 상세, 상품 상세, 사용자 프로필처럼 한 번에 읽는 단위가 명확한 경우
2. **스키마가 빠르게 변하고, 필드 추가/변형이 잦을 때**
   - 실험 단계 기능, 이벤트성 속성, 버전 공존이 필요한 상황
3. **여러 원천 데이터를 비정규화해 읽기 최적화 문서로 유지할 때**
   - CQRS/read model 패턴에서 API 응답 전용 저장소로 사용할 때
4. **중첩 구조(JSON) 자체를 자주 다룰 때**
   - 계층형 구조를 그대로 보관/조회하는 것이 자연스러운 도메인

주의할 점은, 이런 장점은 대부분 **명확한 접근 패턴과 운영 규칙**이 있을 때만 안정적으로 나온다는 것이다.

## 언제 MySQL 같은 RDB가 유리해질 수 있나

다음 상황에서는 RDB가 기본 선택이 되는 경우가 많다.

1. **강한 정합성과 명확한 트랜잭션 경계가 중요할 때**
   - 주문/결제/정산처럼 상태 전이가 엄격해야 하는 도메인
2. **다양한 조건 조합 조회와 관계 질의가 핵심일 때**
   - 다대다 관계, 복잡한 필터, 통계성 질의가 많은 경우
3. **스키마 제약(외래키/유니크/체크)으로 데이터 품질을 강하게 통제할 때**
4. **팀의 SQL 운영 역량과 관측/튜닝 경험이 이미 충분할 때**

실무에서 “관계형 데이터 + 복잡한 조회 요구”가 커질수록, RDB의 쿼리 최적화/제약 기반 운영 강점이 크게 작동한다.

## MSA에서는 ‘원천 저장소’와 ‘조회 저장소’를 분리해서 보자

MSA에서는 한 서비스의 원천 데이터(트랜잭션 소스)와 API 응답용 조회 저장소를 같은 기준으로 비교하면 혼선이 생긴다.

- **원천 저장소(write model)**: 정합성, 트랜잭션, 복구 용이성 중심
- **조회 저장소(read model)**: 응답 속도, 형태 적합성, 조합 비용 최소화 중심

예를 들어 주문/결제의 원천은 RDB에 두고, API 게이트웨이에서 자주 쓰는 통합 응답은 별도 문서 저장소(예: MongoDB)에 비정규화해 둘 수 있다. 다만 이건 “항상 정답”이 아니라, **동기화 지연 허용치·운영 복잡도·재처리 전략**을 감당할 수 있을 때의 선택이다.

## “여러 서비스 데이터를 모아 문서 저장소에 둔다”는 패턴, 가능하지만 만능은 아니다

이 패턴은 분명 유효하다. 특히 아래 효과가 있다.

- API 응답을 한 번에 반환하기 쉬움
- 서비스 간 런타임 호출 의존도 감소
- 읽기 경로의 지연 변동성 완화

하지만 대가도 분명하다.

- 데이터 동기화 파이프라인 운영 필요
- 결국 최신성이 아닌 “허용 가능한 최신성”을 다루게 됨
- 재처리/백필(backfill)/스키마 진화 비용이 누적됨

그래서 실무에서는 “모든 API를 read model로”가 아니라, **지연 민감도가 높은 핵심 조회**부터 제한적으로 도입하는 방식이 보통 더 안전하다.

## Go + MongoDB: 유연한 스키마와 타입 안정성 사이의 설계 포인트

Go는 정적 타입 언어라서, MongoDB의 유연한 문서와 만날 때 의도적인 경계 설계가 필요하다.

- 도메인 모델과 저장 모델(BSON 태그 struct)을 분리해 변경 영향을 줄인다.
- 버전 필드(`schema_version`)를 두고 점진 마이그레이션 경로를 만든다.
- 입력/출력 DTO를 명확히 나눠서 “없음”과 “기본값”을 구분한다.

짧은 실무 포인트:

- optional 필드는 `*T` 또는 nullable 타입으로 표현해 **누락과 zero value를 구분**한다.
- `omitempty`는 편리하지만, “보내지 않음”과 “0/빈문자열을 명시” 의미가 섞이지 않게 API 계약을 먼저 정한다.
- 업데이트 시 전체 치환보다 필드 단위 업데이트를 사용하고, 누락 필드가 의도치 않게 덮어써지지 않도록 주의한다.

## 결론

MongoDB와 MySQL의 조회 성능 비교는 “누가 더 빠른가”보다, **어떤 조회를 어떤 데이터 모델로 어떤 운영 규칙 아래 처리하느냐**의 문제에 가깝다.

- 조인 없는 단순 조회에서는 문서 모델이 유리해 보일 수 있다.
- 그러나 실제 성능은 데이터 모델/인덱스/쿼리 패턴/응답 조립 방식의 영향이 더 크다.
- MSA에서는 원천 저장소와 조회 저장소를 분리해, 트레이드오프를 드러낸 설계를 해야 한다.

정리하면, 특정 DB를 일반론으로 고정하기보다 **요구사항의 안정성·정합성·응답 형태·운영 복잡도**를 기준으로 선택하는 편이 실무적으로 더 재현 가능하다.
