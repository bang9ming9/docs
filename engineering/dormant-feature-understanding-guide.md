# 코드에는 있지만 아직 켜지지 않은 기능, dormant feature 이해하기

## 1) dormant feature라는 표현을 마주친 배경

실무에서 릴리스 노트를 보거나 코드 리뷰를 하다 보면 이런 문장을 자주 본다.

- “이 기능은 이미 배포되었고, 지금은 dormant 상태입니다.”
- “코드는 들어갔지만 아직 켜지지 않았어요.”

처음 보면 “비활성 기능(disabled feature) 얘기인가?” 정도로 받아들이기 쉽다. 그런데 운영 맥락에서 보면 이 표현은 단순히 꺼져 있다는 의미보다 조금 더 구체적이다. 핵심은 **기능 구현물은 운영 코드/배포물에 존재하지만, 공개 시점은 의도적으로 뒤로 미뤄둔 상태**라는 점이다.

즉, “아직 안 만든 기능”이 아니라 “만들어져 있고 배포도 되었지만, 조건이 갖춰질 때까지 의도적으로 활성화하지 않는 기능”을 설명할 때 dormant feature라는 표현이 자연스럽다.

## 2) dormant가 의미하는 기능 상태

`dormant`는 개발 문맥에서 보통 **현재는 활동하지 않지만, 다시 활성화될 수 있는 상태**를 가리킨다. 그래서 dormant feature를 말할 때는 다음 뉘앙스가 함께 있어야 한다.

- 지금은 사용자에게 열려 있지 않다.
- 하지만 기능 코드 자체는 존재한다.
- 특정 조건(설정, 권한, 외부 의존성, 배포 타이밍)이 맞으면 나중에 켤 수 있다.

이 때문에 dormant feature는 “오래 안 쓰는 기능”이나 “사실상 폐기된 죽은 기능(dead feature)”과 다르다. dormant는 **향후 활성화를 전제한 대기 상태**에 더 가깝다.

## 3) feature flag, gated feature, disabled feature 등 관련 표현과의 차이

실무에서 헷갈리기 쉬운 포인트는 이것이다.

- **dormant feature는 기능의 상태를 설명하는 말**이고,
- **feature flag / feature toggle은 그 상태를 제어하는 수단**이다.

예를 들어 “기능은 배포되어 있지만 feature flag 뒤에 숨겨져 dormant 상태로 유지된다”는 표현은 상태와 제어 방식을 분리해서 잘 설명한 문장이다.

함께 자주 등장하는 용어를 짧게 구분하면 다음과 같다.

- **disabled feature**: 지금 꺼져 있다는 사실 자체를 말할 때 무난하다. 다만 “나중에 켤 계획”까지 강하게 담지는 않는다.
- **inactive feature**: disabled와 비슷하게 중립적 표현이다. 상태 설명에는 좋지만 운영 의도(왜 꺼져 있는지)는 덜 드러난다.
- **gated feature**: 접근 조건(플래그, 권한, 설정, 환경 조건)으로 문이 걸려 있음을 강조할 때 적합하다.
- **kill switch**: 장애/리스크 대응을 위해 빠르게 끄는 안전장치를 강조할 때 쓰는 표현이다. 기능 준비 상태 자체보다 비상 차단 목적이 중심이다.
- **dark launch**: 사용자에게는 거의 노출하지 않거나 제한적으로만 노출하면서 운영 환경에서 먼저 검증하는 전략을 말할 때 자연스럽다.

실제 문맥에서는 하나만 쓰기보다 조합해서 설명하면 더 명확하다. 예를 들어 “결제 기능은 dark launch로 배포했고, 현재는 flag로 gating 되어 dormant 상태다”처럼 쓸 수 있다.

## 4) 실무에서 dormant 상태를 두는 이유

dormant 상태는 “배포를 미루기 어려워서 임시로 숨긴다” 수준이 아니라, 운영 리스크를 분리하기 위한 실무 장치로 자주 쓰인다.

1. **코드 배포와 기능 공개를 분리하기 위해**
   - 코드 통합은 미리 해두고, 실제 공개는 비즈니스 일정이나 운영 준비도에 맞춰 별도로 진행할 수 있다.

2. **외부 의존성이 준비되기 전에도 코드 배포를 먼저 진행하기 위해**
   - 외부 API 계약, 정산 계정, 계약 주소 같은 준비물이 늦어져도 내부 코드 배포 파이프라인은 유지할 수 있다.

3. **점진적으로 기능을 열기 위해**
   - 내부 사용자 → 일부 고객 → 전체 고객 순으로 열면 장애 반경을 줄일 수 있다.

4. **문제 발생 시 빠르게 다시 비활성화하기 위해**
   - 롤백 배포보다 설정 전환이 빠른 경우가 많아 운영 대응 시간이 줄어든다.

5. **여러 팀/시스템 간 배포 타이밍을 맞추기 위해**
   - 백엔드, 프런트엔드, 데이터 파이프라인, 외부 파트너가 모두 준비될 때까지 기능을 대기 상태로 둘 수 있다.

## 5) 범용적인 예시

아래는 특정 회사/제품에 묶이지 않는, 자주 겪는 예시들이다.

1. **결제 정산(reconciliation) 로직 전환**
   - 새 정산 로직 코드를 배포해두고, 데이터 마이그레이션이 완료될 때까지 dormant 상태로 유지한다.

2. **외부 API 연동 기능 출시**
   - API 키, 허용 IP, 요금제 한도, SLA 확인이 끝나기 전까지 연동 경로를 열지 않는다.

3. **관리자 승인 플로우/권한 체계 변경**
   - 새 권한 모델을 배포했지만, 운영팀 권한 프로비저닝이 완료될 때까지 inactive로 둔다.

4. **리워드 기능(스마트 컨트랙트 연계 포함)**
   - 앱/서버 코드에는 기능을 반영해두되, 외부 컨트랙트 주소와 ABI가 확정되기 전까지 dormant 상태로 유지한다.

(필요하면 A/B 테스트도 같은 패턴으로 설명할 수 있다. 실험군 배정 조건이 준비되기 전까지는 기능이 배포되어 있어도 열지 않는다.)

## 6) 운영 시 주의할 점

중요한 점: **dormant는 안전 보장을 의미하지 않는다.**

코드가 운영 환경에 존재한다면, “꺼져 있으니 괜찮다”라고 단정하면 위험하다. 설정 실수, 기본값 오류, 우회 호출, 권한 누락으로 의도치 않게 실행될 수 있기 때문이다.

체크 포인트를 보수적으로 보면 좋다.

- 기본값이 정말 `off`인지
- 활성화 조건(플래그/설정/권한/환경)이 문서와 코드에서 일치하는지
- 설정 누락/오류 시 안전하게 실패(fail-safe)하는지
- UI만 숨긴 것이 아니라 API/백엔드 경로도 보호되는지
- 권한 있는 사용자(또는 시스템)만 활성화할 수 있는지
- 문제가 생기면 즉시 다시 끌 수 있는지
- 로그/모니터링/알림으로 의도치 않은 접근을 탐지할 수 있는지

특히 API 직접 호출 가능성이 있는 시스템에서는 “버튼이 안 보인다”는 이유만으로 dormant를 보장할 수 없다. 서버 측 제어 조건과 권한 검증이 함께 있어야 한다.

## 7) 문서나 코드 리뷰에서 어떻게 표현하면 좋은지

“The feature is dormant.”라고만 적으면 정보가 부족할 수 있다. 실제 협업 문서에서는 최소한 다음이 드러나는 편이 좋다.

- 기능 코드가 이미 배포되었는지
- 어떤 조건이 충족되어야 활성화되는지
- 어떤 방식(플래그/설정/권한/환경 조건)으로 비활성 상태를 유지하는지
- 활성화 절차와 롤백(재비활성화) 절차가 있는지

다음처럼 쓰면 오해가 줄어든다.

- “The payment reconciliation feature is deployed but remains dormant behind a feature flag until the migration is completed.”
- “The admin approval flow is gated by a configuration flag and should remain inactive until the required permissions are provisioned.”
- “The reward feature can be activated after the external contract address and ABI are configured.”

리뷰 코멘트에서도 같은 원칙을 적용할 수 있다. 예를 들어 “지금 꺼져 있음”만 확인하지 말고, **누가/어떤 절차로 켜고 다시 끄는지**까지 확인하면 운영 사고 가능성을 줄일 수 있다.

## 8) 짧은 결론

dormant feature는 “죽은 기능”이 아니라, **배포는 되었지만 의도적으로 아직 활성화하지 않은 기능 상태**를 설명하는 실무 용어다. 이 상태를 이해하면 “왜 코드가 있는데 기능은 안 열렸지?”라는 질문에 더 정확히 답할 수 있다.

실무에서는 상태(dormant)와 제어 수단(feature flag, configuration gating 등)을 구분해서 기록하고, 활성화 조건·안전장치·롤백 절차를 함께 문서화하는 것이 중요하다. 결국 핵심은 “꺼져 있음”이라는 한 줄이 아니라, **운영 환경에 이미 존재하는 코드로서 어떻게 통제되는가**를 명확히 남기는 것이다.
