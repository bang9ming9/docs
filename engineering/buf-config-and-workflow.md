# 실무 관점에서 정리하는 Buf 기반 Protobuf 운영: `buf.yaml`과 `buf.gen.yaml`, 그리고 `protoc` 대비 선택 기준

## 배경: 왜 이 주제를 따로 정리하는가

Protobuf를 처음 도입할 때는 `protoc` 명령을 직접 호출해도 큰 문제가 없어 보인다. 파일 수가 적고 서비스가 한두 개일 때는, 생성 명령을 README나 Makefile에 적어두는 방식만으로도 운영이 가능하다.

하지만 실제 운영 단계로 가면 상황이 달라진다. 스키마가 늘고, 서비스가 분리되고, 팀원이 늘어나면서 다음과 같은 질문이 반복된다.

- 어떤 규칙으로 `.proto`를 작성해야 하는가
- 어떤 기준으로 하위 호환성(breaking change)을 확인할 것인가
- 어떤 플러그인으로 어느 경로에 코드를 생성해야 하는가
- 로컬 환경마다 생성 결과가 달라지는 문제를 어떻게 줄일 것인가

이 지점에서 Buf는 단순한 생성 커맨드 래퍼라기보다, **스키마를 팀 단위로 일관되게 관리하기 위한 운영 도구**로 이해하는 편이 실무에 더 가깝다.

---

## `buf.yaml`과 `buf.gen.yaml`: 이름은 비슷하지만 책임은 다르다

실무에서 가장 자주 생기는 혼동은 “어떤 설정을 어디에 둬야 하느냐”다. 핵심은 다음처럼 나누는 것이다.

- `buf.yaml`: **스키마 자체를 어떻게 관리할지**
- `buf.gen.yaml`: **스키마로부터 무엇을 생성할지**

### 1) `buf.yaml`이 담당하는 것

`buf.yaml`은 workspace 차원의 공통 스키마 관리 기준을 정의하고, 그 안에 하나 이상의 module 구성을 둘 수 있는 설정이다. 보통 다음 책임이 들어간다.

- module/workspace 관점의 기준점
- lint 규칙
- breaking change 검사 정책
- 외부 dependency(예: 공유 proto 모듈) 선언

즉, “우리 팀이 어떤 스키마를 어떤 규칙으로 유지할 것인가”를 정의하는 파일에 가깝다.

짧은 예시는 아래처럼 볼 수 있다.

```yaml
version: v2
modules:
  - path: proto
lint:
  use:
    - STANDARD
breaking:
  use:
    - FILE
deps:
  - buf.build/acme/common
```

위 예시에서 `deps`의 dependency는 BSR 기준 모듈 의존성을 뜻한다. 로컬 경로나 일반 Git URL을 그대로 넣는 용도로 이해하기보다, 스키마 모듈 의존성 선언으로 보는 편이 안전하다.

위 예시의 핵심은 구문 자체보다 책임 범위다. lint/breaking/dependency는 생성 대상 언어(Go, Java, TS 등)와 무관하게, 스키마 운영 규칙에 속한다.

### 2) `buf.gen.yaml`이 담당하는 것

`buf.gen.yaml`은 코드 생성 파이프라인 설정이다. 즉 “어떤 플러그인을 사용해 어떤 결과물을 어디에 생성할지”를 정의한다.

- plugin 종류(remote/local)
- plugin별 옵션(opt)
- 출력 경로(out)
- 필요 시 입력 경로 제어

짧은 예시는 아래와 같다.

```yaml
version: v2
plugins:
  - remote: buf.build/protocolbuffers/go
    out: gen/go
    opt:
      - paths=source_relative
  - local: protoc-gen-go-grpc
    out: gen/go
    opt:
      - paths=source_relative
```

여기서 중요한 점은 remote/local 모두 가능하다는 사실 자체보다, **팀이 재현 가능한 생성 기준을 한 파일에 모아둘 수 있다**는 점이다. 어느 방식이 항상 정답이라고 단정하기보다, 보안/캐시/도구 버전 통제/네트워크 제약 같은 운영 조건으로 선택하는 것이 현실적이다.

## `protoc` 직접 호출 방식에서 커지는 불편함

작은 프로젝트에서는 `protoc -I ... --go_out=... --go-grpc_out=...` 같은 명령을 스크립트에 두고 운영할 수 있다. 문제는 규모가 커졌을 때다.

### 관찰되는 현상

- include path가 서비스별 스크립트에 분산됨
- plugin 옵션이 언어/팀별로 조금씩 달라짐
- 실행 위치(working directory) 의존성 때문에 CI와 로컬 결과 차이가 생기기 쉬움
- 생성 대상 경로 규칙 불일치가 팀별 스크립트 운영 방식에 따라 더 두드러질 수 있음
- lint/breaking 검사가 생성 과정과 분리되어 운영됨

### 일반적인 해석

이 문제들은 `protoc` 자체의 결함이라기보다, **직접 호출 기반 운영에서 표준화 책임이 팀 스크립트에 흩어지기 쉬운 구조**에서 자주 발생한다. 프로젝트가 커질수록 “누가 어떤 옵션으로 생성했는지”를 재현하기 어려워지는 이유도 여기에 있다.

## Buf를 쓰면 무엇이 정리되는가

Buf를 도입한다고 해서 Protobuf 운영 문제가 자동으로 해결되지는 않는다. 다만 운영 관점을 다음처럼 정리하기 쉬워진다.

1. 스키마 정책(`buf.yaml`)과 생성 정책(`buf.gen.yaml`)을 분리할 수 있다.
2. `generate`, `lint`, `breaking`을 한 흐름으로 묶어 CI 파이프라인에 올리기 쉽다.
3. 모듈/의존성 관리를 통해 공유 proto 사용 시 변경 파급을 추적하기 쉬워진다.
4. monorepo, 다중 서비스, 공유 스키마 환경에서 공통 규칙을 코드화하기 수월하다.

특히 monorepo나 다중 서비스 구조에서는 “각 서비스가 제각각 protoc 스크립트를 들고 있는 상태”가 장기적으로 유지 비용을 키우는 경우가 많다. Buf는 이 지점을 줄이는 데 유리할 수 있다. 단, 저장소 구조와 릴리스 전략이 정리되지 않으면 Buf를 써도 생성물 배치 문제나 패키징 문제는 계속 남는다.

## 실무에서의 판단 기준과 주의점

아래는 도입 여부를 판단할 때 자주 쓰는 체크 포인트다.

### 판단 기준

- 서비스 수와 `.proto` 파일 수가 증가하는 추세인가
- 스키마 호환성 검증을 CI에서 일관되게 강제할 필요가 있는가
- 여러 언어/런타임으로 코드 생성을 반복하는가
- 공유 proto를 여러 팀이 함께 관리하는가

### 주의점

- remote plugin과 local plugin은 운영 제약에 따라 선택해야 하며, 한쪽이 보편적으로 우월하다고 보기 어렵다.
- `go_package`, generated 코드 위치, 출력 디렉터리 전략은 Buf만으로 결정되지 않는다. 저장소 구조와 배포 방식까지 함께 설계해야 한다.
- BSR/외부 dependency를 사용할 때도 권한 정책, 캐시 전략, 네트워크 제약을 먼저 확인하는 편이 안전하다.

즉, Buf는 “도구 하나로 모든 문제가 해결된다”는 접근보다, **스키마 거버넌스를 명시적으로 운영하기 위한 기반**으로 보는 것이 균형 잡힌 해석이다.

---

## 짧은 결론

`protoc` 직접 호출은 작은 규모에서 빠르게 시작하기 좋다. 반면 팀/서비스/스키마가 함께 커지는 환경에서는 include path, plugin 옵션, 실행 방식이 분산되며 운영 복잡도가 올라가기 쉽다.

Buf의 실무적 가치는 생성 명령 대체 그 자체보다, `buf.yaml`(스키마 정책)과 `buf.gen.yaml`(생성 정책)을 분리해 lint/breaking/generate를 한 흐름으로 관리할 수 있다는 점에 있다. 다만 plugin 선택, 출력 구조, dependency 전략은 팀 환경에 따라 달라지므로, 도입 자체보다 운영 원칙을 함께 설계하는 것이 중요하다.
