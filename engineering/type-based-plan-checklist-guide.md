# 작업 계획서를 더 잘 검토하기 위한 type 기반 체크리스트

## 왜 이런 포맷이 필요한가

AI를 활용하면 작업 계획서 초안은 빠르게 만들 수 있다. 다만 계획서가 빨리 나온다는 사실과, 계획서가 충분히 검토 가능하다는 사실은 다르다. 실제 검토에서는 변경의 성격에 따라 놓치기 쉬운 위험이 달라지기 때문이다.

예를 들어 `fix` 성격의 변경은 재현 가능성, 원인 추적, 회귀 방지가 핵심이다. 반대로 `migration` 성격의 변경은 롤백 경로, 데이터 보존, 배포 순서가 더 중요해진다. 같은 템플릿으로만 검토하면 어떤 변경에서는 필요한 질문이 빠지고, 다른 변경에서는 불필요한 확인이 늘어나 검토 피로만 커질 수 있다.

그래서 실무에서는 공통 체크 항목 위에 변경 type별 추가 체크리스트를 붙이는 방식이 유용하다. 핵심은 계획서를 정교하게 분류하는 것이 아니라, 검토자가 초기에 위험 신호를 빠르게 발견하도록 돕는 것이다.

## 이 포맷의 설계 원칙

### 1) `type`은 엄밀한 taxonomy가 아니라 검토 키다

`type`은 모든 작업을 완벽하게 분류하기 위한 체계가 아니다. 계획서를 읽는 사람이 어떤 실패 패턴을 먼저 의심해야 하는지 알려주는 실무용 힌트에 가깝다.

### 2) 과분류하지 않는다

유형이 지나치게 많아지면 선택이 어려워지고, 분류 자체가 추가 업무가 된다. 대체로 팀이 반복적으로 쓰는 소수의 type만 유지하는 편이 운영 비용이 낮다.

### 3) 애매하면 기본값으로 둔다

일부 작업은 여러 성격이 섞여 보일 수 있다. 이때는 가장 주된 변경 의도를 기준으로 하나를 우선 선택하고, 나머지는 체크리스트 항목으로 보완하는 편이 실용적이다. 운영 흔들림을 줄이려면 팀마다 애매한 경우에 쓰는 기본 fallback type 하나를 가볍게 정해두는 것도 좋다. 이 기준이 있으면 계획서 작성과 검토 기준이 덜 흔들린다.

### 4) type 미선언도 허용한다

초기 탐색 단계나 범위가 아직 흔들리는 작업에서는 type을 확정하지 않아도 된다. 대신 검토 시점에는 최소한 어떤 위험을 우선 확인할지 명시하는 편이 좋다.

### 5) 조합은 최소화한다

복수 type은 필요할 때만 제한적으로 사용한다. 조합이 많아질수록 리뷰 기준이 불명확해지고, 변경 이력 해석이 어려워진다.

### 6) `test`, `docs`는 역할을 분리해 본다

`test`, `docs`는 많은 작업에 함께 따라오는 부수 변경이다. 따라서 테스트 추가나 문서 수정이 "항상" 별도 type이라는 의미는 아니다. 테스트 자체 설계가 주된 산출물일 때만 `test`를 주 type으로 쓰고, 문서가 주 deliverable일 때만 `docs`를 주 type으로 쓰는 편이 더 명확하다.

## 타입 정의

| type | 의미 | 주된 확인 포인트 |
|---|---|---|
| `feat` | 기존에 없던 사용자 가치나 기능을 추가하는 변경 | 요구사항 범위, 수용 기준, 하위 호환성, 운영 영향 |
| `fix` | 이미 기대되던 동작을 회복하는 변경 | 재현 스텝, 원인 설명, 회귀 방지, 유사 경로 점검 |
| `refactor` | 외부에서 관찰 가능한 동작을 유지한 채 내부 구조를 개선하는 변경 | 동작 동일성 근거, 인터페이스 비변경 확인, 성능 회귀 |
| `perf` | 기능 의미는 유지하면서 성능 특성을 개선하는 변경 | baseline, 측정 조건, 목표 지표, 비교 공정성 |
| `migration` | 데이터/스키마/프로토콜/운영 절차를 새 상태로 전환하는 변경 | 롤백 전략, 데이터 보존, 배포 순서, 사전 검증 |
| `security` | 위협 노출을 줄이거나 취약점을 완화하는 변경 | 위협 모델, 패치 범위 통제, 유사 취약 지점 점검 |
| `infra` | 서비스 운영 기반(빌드/배포/관측/인프라 구성)을 변경하는 작업 | 배포 안전성, 운영 가시성, 장애 전파 범위 |
| `test` | 테스트 자산 자체가 주된 산출물인 변경 | 검증 대상 명확성, 실패 시 신호 품질, 유지보수성 |
| `docs` | 문서 자체가 주된 산출물인 변경 | 정확성, 최신성, 독자 관점 재현 가능성 |
| `chore` | 기능/구조 핵심과 직접 무관한 유지관리성 작업 | 자동화 안정성, 반복 작업 감소, 영향 범위 제한 |
| `spike` | 폐기를 전제로 가설을 검증하는 탐색/실험 작업 | 가설·성공 기준·종료 조건·폐기 계획 |

## 타입별 추가 체크 예시

아래 항목들은 "반드시 동일하게" 적용해야 하는 규칙이 아니라, 해당 type에서 자주 놓치는 위험을 먼저 드러내기 위한 점검 질문이다.

### `fix`

- 재현 스텝: 문제가 실제로 다시 발생하는지 확인할 수 있어야 수정 효과를 검증할 수 있다.
- 근본 원인 가설: 단순 증상 완화인지, 원인 제거인지 구분해야 같은 결함이 다른 경로에서 재발하는 것을 줄일 수 있다.
- 회귀 테스트: 동일 결함이 미래 변경에서 다시 들어오지 않도록 최소한의 자동 검증 고정점이 필요하다.
- 같은 원인의 다른 경로 검토: 입력 경로나 상태 조합이 다르면 같은 원인이 다른 형태로 남아 있을 수 있다.

### `refactor`

- 외부 관찰 가능한 동작 유지 근거: "동작 동일"을 주장하려면 비교 기준(기존 테스트, 계약 테스트, 결과 diff 등)이 제시되어야 한다.
- API/이벤트/저장 포맷/스키마 변경 여부 명시: 의도치 않은 계약 변경은 리팩터링 리스크를 가장 크게 만든다.
- 새 기능 추가 혼입 방지: 구조 개선과 기능 추가를 섞으면 리뷰가 어려워지고 결함 원인 분리가 늦어진다.
- 성능 회귀 검토: 구조가 바뀌면 기능은 같아도 지연 시간·메모리·쿼리 패턴이 달라질 수 있다.

### `migration`

- 롤백 경로: 전환 실패 시 어느 시점까지 어떻게 되돌릴 수 있는지 사전에 정의해야 운영 위험을 줄일 수 있다.
- 데이터 손실 가능성과 영향 범위: 어떤 데이터가 손실·변형될 수 있는지, 영향 사용자가 누구인지 명시해야 대응 우선순위를 정할 수 있다.
- 코드와 스키마의 배포 순서: 순서가 어긋나면 짧은 시간에도 읽기/쓰기 불일치가 발생할 수 있다.
- dry-run 또는 사전 검증 계획: 실제 전환 전에 대표 표본으로 검증하면 대규모 실패 가능성을 낮출 수 있다.

### `perf`

- baseline 수치: 개선 전 수치가 없으면 개선 여부를 판단할 기준이 없다.
- 측정 방법/환경: 도구, 부하 패턴, 데이터 크기, 캐시 상태가 다르면 결과 해석이 달라진다.
- 정량 목표: "빨라졌다"가 아니라 목표값이나 허용 범위를 제시해야 의사결정이 가능하다.
- 같은 조건에서 비교 가능한 측정인지: 조건이 다르면 성능 향상과 실험 편향을 구분하기 어렵다.

### `security`

- 어떤 위협이나 공격 시나리오를 줄이려는지: 방어 목적이 분명해야 패치의 적절성을 평가할 수 있다.
- 패치 범위가 과도하게 커지지 않는지: 보안 수정은 긴급성이 높아도 변경 반경을 통제해야 새 결함 유입을 줄일 수 있다.
- 유사 패턴의 횡적 검토: 같은 실수가 다른 모듈에 반복되어 있을 가능성이 높다.
- 가능한 경우 공격 회귀 검토: 알려진 공격 벡터가 다시 통과하지 않는지 확인해야 수정의 지속성을 확보할 수 있다.

## 조합 원칙

복수 type은 완전히 금지할 필요는 없지만, 검토 관점이 충돌하지 않는 조합만 제한적으로 허용하는 편이 보통 유리하다.

자연스러운 조합 예시는 다음과 같다.

- `[fix, test]`: 버그 복구와 회귀 고정이 한 단위로 읽힌다.
- `[feat, docs]`: 신규 기능과 사용자/운영 문서 보완이 함께 전달된다.
- `[feat, migration]`: 기능 출시와 데이터/스키마 전환이 본질적으로 연결될 수 있다.
- `[refactor, test]`: 동작 동일성 검증을 테스트 강화로 보완하기 쉽다.
- `[security, test]`: 취약점 완화와 공격 회귀 검증을 같이 설명하기 좋다.
- `[fix, docs]`: 장애 원인·우회 절차·운영 가이드 보완이 함께 필요한 경우가 있다.

가능하면 분리하는 편이 좋은 조합은 다음과 같다.

- `[refactor, fix]`: 구조 개선과 결함 수정을 분리하면 리뷰 초점이 선명해지고, 이슈 원인 추적과 `git bisect` 효율이 좋아진다.
- `[refactor, feat]`: 새 기능 효과와 구조 변경 효과가 섞이면 성능·안정성 회귀 원인을 분해하기 어렵다.
- `[feat, perf]`: 기능 추가와 성능 개선을 분리하면 롤백 시 선택지가 늘고, 성능 지표 해석이 명확해진다.
- `[migration, refactor]`: 전환 리스크와 내부 구조 리스크를 분리해야 배포/롤백 계획이 단순해지고 사고 대응이 빨라진다.

요약하면, 조합 정책의 목적은 형식 통일이 아니라 리뷰 속도, 변경 추적성, 롤백 가능성, 히스토리 해석 용이성을 높이는 데 있다.

## 예시 포맷

아래는 계획서 머리글(front-matter)에 들어갈 수 있는 간단한 예시다.

단일 타입 예시
- title: 결제 취소 중복 처리 버그 수정
- type: fix

자연스러운 조합 예시
- title: 신규 배치 집계 API 추가와 운영 가이드 보완
- type: [feat, docs]

예외적으로 혼합이 필요한 경우 예시
- title: 인증 토큰 검증 취약점 패치와 공격 회귀 테스트 추가
- type: [security, test]
- note: 긴급 패치로 단일 변경으로 묶되, 후속 분리 작업 계획을 함께 기록

## 마무리

좋은 계획서는 길고 복잡한 계획서라기보다, 변경의 리스크와 검증 방법이 빠지지 않고 드러나는 계획서에 가깝다. `type`과 체크리스트는 계획서를 예쁘게 분류하기 위한 장치가 아니라, 사람이 더 빠르고 정확하게 검토하기 위한 최소한의 구조로 보는 편이 실무에 잘 맞는다.

특히 AI가 작성한 계획서를 다룰 때는 초안 속도보다 검토 가능성이 더 중요해진다. 단순하고 반복 가능한 type 설계와 체크리스트 운영은 검토 품질을 안정적으로 관리하고 변경 검토의 일관성을 유지하는 데 도움이 된다.
