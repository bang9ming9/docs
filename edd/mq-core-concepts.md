# 메시지 큐 핵심 개념 정리 (RabbitMQ / SQS 구분 중심)

## 짧은 도입
메시지 기반 아키텍처는 **요청 처리와 후속 작업을 분리**해 비동기 처리, 서비스 간 결합도 완화, 트래픽 완충을 가능하게 하기 위해 사용한다. 예를 들어 Go 백엔드에서 주문 API는 빠르게 응답하고, 알림/정산 연동은 큐를 통해 비동기로 처리할 수 있다.

## 핵심 용어 정리
- **Producer**: 메시지를 보내는 쪽(예: API 서버).
- **Consumer**: 메시지를 받아 처리하는 쪽(예: 워커).
- **Queue**: 메시지가 쌓여 대기하는 위치.
- **Broker**: 메시지를 수신, 저장, 전달하는 메시징 시스템(RabbitMQ, SQS). 전달 신뢰성은 브로커 기능뿐 아니라 설정과 소비자 처리 방식에도 영향을 받는다.
- **Exchange (RabbitMQ 중심)**: 들어온 메시지를 어떤 Queue로 보낼지 라우팅하는 계층.
- **Ack / Nack**: 주로 RabbitMQ 같은 브로커에서 소비자가 처리 성공/실패를 브로커에 알리는 방식. SQS는 보통 성공 시 메시지 삭제, 실패 시 visibility timeout 이후 재수신으로 다룬다.
- **Retry**: 일시 실패 시 재시도. 횟수/간격(백오프) 정책이 필요.
- **DLQ**: 반복 실패 메시지를 격리해 운영적으로 추적·분석하는 큐.
- **Idempotency**: 중복 메시지를 받아도 결과가 한 번 처리한 것과 같아야 하는 성질.
- **Ordering / FIFO**: 순서 보장은 브로커/큐 타입/설정에 따라 달라지며 일반화하면 안 된다.

## RabbitMQ와 SQS 차이
- **RabbitMQ**: Exchange + Binding 기반 라우팅이 핵심. 라우팅 유연성이 높다.
- **SQS**: Queue 중심 모델. RabbitMQ처럼 Exchange를 두고 라우팅하는 구조가 기본이 아니다.
- **공통점**: 실무에서는 둘 다 중복 수신 가능성을 전제로 소비자를 설계하는 것이 안전하다.
- **주의**: FIFO/순서 보장은 “브로커 이름”이 아니라 “사용한 큐 유형과 설정”으로 판단해야 한다.

## 실무에서 꼭 기억할 포인트
1. 재시도는 무조건 많이가 아니라, **일시 장애만 구제**하도록 제한한다.
2. DLQ는 실패를 버리는 통이 아니라 **원인 파악을 위한 운영 장치**다.
3. 중복 수신 가능성을 고려해 Consumer에 idempotency 또는 중복 감지 전략을 둔다.
4. “순서 보장” 요구가 있으면 초기 설계에서 큐 타입과 키 설계를 먼저 확정한다.

## 마무리
입문 단계에서는 “Producer가 보내고, Consumer가 처리하며, 실패는 Retry/DLQ로 통제한다”만 정확히 잡아도 충분하다. 그 위에 RabbitMQ(라우팅 중심)와 SQS(큐 중심)의 구조 차이를 구분하면 실무 설계 판단이 훨씬 쉬워진다.
